Lesson 01

The big picture

Three ways to work with Claude. Same brain, three different bodies.

LAYER 1

Claude chat

A conversation in the browser. You ask, it answers — it can search, read uploads, write documents. For thinking, writing, learning.

Limit: everything disappears when the chat ends. It can't touch your computer.

LAYER 2

Cowork

Claude works on a folder of your files: reads documents, organizes them, produces new ones — no copy-pasting.

Limit: it works on files, not systems. It doesn't build software or publish anything.

LAYER 3 · THIS COURSE

Claude Code

Claude gets hands. It runs in your terminal inside a project, reads and writes files, runs programs, uses git, deploys to the internet.

Limit: with hands comes responsibility — most of this course is about steering it safely.

The AI competence ladder

AI skill isn't one thing you have or don't — it's a ladder, and almost everyone is on the bottom rungs. Rough shares of professionals today:

LevelNameOne line~Share
0UnawareStill doing everything manually; hasn't really tried AI10–20%
1AwareHas tried ChatGPT or Claude; occasional, not part of how they work15–25%
2Assisted workerUses AI daily to draft, summarize, think; real hours saved weekly25–35%
3Enabled professionalYou, after this course. AI embedded in how you work; delegates multi-step tasks; builds real things with Claude Code12–20%
4Workflow integratorConnects AI to real systems; ships working products to the internet6–12%
5System builderDesigns systems of coordinated AI agents with checkpoints2–5%
6–9Architect → frontierProduction platforms, AI products with real users, defining how the field works<2%

Three things to take from this: you are probably at 0–2, and so is almost everyone — the ladder is young. This course targets Level 3 with a real glimpse of 4 (a deployed product), which already puts you ahead of roughly 80% of professionals. And the floor keeps rising: what needed a senior engineer in 2024 is a Level-3 skill with today's tools. One level per year is a realistic pace — and each level compounds, because the systems you build keep working for you.

The level is a diagnosis, not a badge. Re-read the table after session 4 and place yourself again.

Lesson 02

Key concepts

A dozen words that make everything else make sense. The analogies are imperfect but load-bearing.

1LLM / model

The "brain": a program trained on enormous amounts of text that predicts what comes next — which turns out to be enough to converse, write, and code. Bigger models (Opus-class) are smartest and priciest; mid models (Sonnet-class) are the daily driver; small ones (Haiku-class) are fast and cheap.

Analogy: hiring. Sometimes the senior architect, usually the solid contractor, apprentices for repetitive work.

Key point: the model has no memory between conversations. Everything it "knows about you" must be given to it every time — which is why the next two concepts matter most.

2Tokens

The units the model reads and writes — roughly word-fragments (~¾ of a word). Every AI service bills by tokens in + tokens out, like a utility bills by kWh. Tokens are the cost meter and the memory meter.

3Context window — and the "dumb zone"

The model's working memory: everything it can see right now — instructions, the conversation, files it has read. Large but finite. The trap: performance doesn't fall off a cliff when it fills; it degrades gradually. Matt Pocock calls the last stretch the dumb zone — the conversation still works, but the model starts forgetting instructions and making sloppy mistakes.

Analogy: a workbench. Big, but buried under every tool of the day, work gets sloppy. The fix isn't a bigger bench — it's clearing it.

Memorize this rule: short, focused sessions. Task done → start fresh. Never push "one more thing" deep into the dumb zone.

4Prompt & system prompt

A prompt is what you type. A system prompt is the standing instructions the model receives first — its job description. Good prompting for beginners is mostly: say what you want, what "done" looks like, and what to avoid — like briefing a very fast, very literal new hire.

5Repo

A project folder with a memory: your files plus the full history of every change ever made (kept by a tool called git). See what changed, when, and roll anything back. GitHub is the website where repos live online.

Analogy: a document with unlimited, perfectly organized "track changes" — for a whole folder.

Why it's the killer feature for AI work: the undo button gives you courage. If Claude Code wrecks something, roll back in one command. You will never lose work — so the AI can work boldly.

6Markdown

Plain text files with simple formatting marks (# heading, **bold**, - list). It's text, and models are text machines — your notes, plans, and instructions to Claude are all markdown. The paper of the AI workshop.

7CLAUDE.md

A markdown file in your repo that Claude Code reads automatically at the start of every session. Whatever you write there — "this project is X", "always do Y", "never touch Z" — becomes standing orders.

Analogy: the laminated instruction sheet taped to the workshop wall. New assistant walks in, reads it, knows the house rules.

The single highest-leverage file you'll ever write. Teaching the file beats repeating yourself every session.

8Scripts

Small programs that do one job. Claude Code writes them constantly: "a script that renames these photos by date". You don't write scripts — you know to ask for one. Rule of thumb: doing something tedious a third time? Ask for a script.

9Agents

An AI that doesn't just answer — it acts in a loop: try, look at the result, adjust, try again, until the goal is met. Claude Code is an agent: ask it to fix a bug and it reads, changes, tests, sees the failure, fixes, reruns.

Analogy: asking for directions (chat) vs hiring a driver (agent).

10Skills

Packaged know-how you give Claude Code: a folder of instructions it loads when a matching task appears — "how we write blog posts", "how we deploy". Write once, reuse forever.

Analogy: recipe cards in the workshop drawer. Every lesson you teach the system makes every future session better — the real endgame of this course.

11MCPs and APIs

API: a service's official counter for programs — how software orders things from other software (weather data, email, payments). Usually metered and billed. MCP: a standard plug that connects tools to Claude — calendar, Gmail, a database.

Analogy: APIs are the service counters of every business in town; MCP is the universal adapter that lets your assistant walk up to any of them.

12Hallucination

Models sometimes state false things with total confidence — plausible names, facts, and numbers that don't exist. Not lying; autocomplete overreaching.

The model is a brilliant drafter and a mediocre witness. Anything that matters gets verified — this shapes the whole workflow below.

Lesson 03

Setup: your workshop

Done together in session 2, step by step. Three pieces, one magic circuit.

ToolRoleAnalogy
VS CodeThe editor — where you see and edit files; Claude Code runs in a panel inside itThe workshop: bench, good lighting
GitHubOnline home of your repos: backup, history, sharingThe warehouse with a ledger of every change
VercelWatches your GitHub repo; every change auto-publishes to the live internetThe delivery service: goods → shelf, automatically

The magic circuit: edit in VS Code → save to GitHub → Vercel publishes → your change is live in about 60 seconds. No servers to manage; free tiers cover everything in this course.

About the terminal

The black window is the honest interface: you type a command, the computer does exactly that. You need about five commands total (cd go to folder, ls list files, claude start Claude Code, git status what changed). Claude Code teaches you the rest — literally ask it "what does this command do?"

The checklist

  1. Install VS Code

    code.visualstudio.com → download, install, open once.

  2. Create a GitHub account

    github.com. Free. Your username becomes public and appears in your project URLs — pick one you're happy to show people.

  3. Install git

    Mac: run git --version in Terminal, accept the install popup. Windows: Git for Windows with defaults.

  4. Install Node.js

    nodejs.org, the LTS version. The runtime many tools are built on — installed once, then invisible.

  5. Install Claude Code

    npm install -g @anthropic-ai/claude-code, then run claude and log in. First thing to try: "look around this folder and tell me what's here."

  6. Create a Vercel account

    vercel.com → "Sign up with GitHub". Notice what you just did: connected two tools. You'll do this a lot.

  7. Set spending limits — before anything else

    Wherever billing exists, find the usage-limit setting and set it now. Non-negotiable house rule — see Principles, rule 6.

When something goes wrong

It will, for at least one of us, and that's fine. The debugging move, itself lesson material: copy the entire error message, paste it to Claude with one line of context ("installing X on a Mac, got this"), do what it says, repeat. You don't need to understand errors — you need to ferry them to something that does.

Lesson 04

The workflow

The loop you'll run for everything, from a typo to a product.

PLAN→ PROMPT→ BUILD→ VERIFY→ DEPLOY

↺ learn & repeat — the loop is fractal: five minutes for a typo, a week of loops for a project

  1. Plan — before any building

    "I want X. Ask me questions until you understand, then propose a plan. Don't write anything yet." Claude Code has a plan mode for exactly this. Better: describe your goal messily, then say "turn this into a clear, detailed brief for yourself" — it writes better prompts than beginners do; you just correct the plan. A wrong plan costs a sentence to fix; wrong code costs a session.

  2. Prompt — the brief

    Approve or edit the plan. Always include what "done" means: "done = the page shows my three projects and looks right on a phone." A brief without a definition of done is a wish.

  3. Build — let it work

    Claude Code edits files, runs commands, checks its own results. Watch loosely; answer its questions. Nothing is final until you commit.

  4. Verify — never skip

    Do not trust, check. Open the result, click every button, read the text out loud. Report what you observed: "the menu overlaps the logo on my phone" gets fixed in one round; "it's broken" gets guesses.

  5. Deploy — ship it

    Commit (a saved checkpoint), push to GitHub, Vercel publishes. Then start a fresh session for the next task — remember the dumb zone. Done → commit → new session is the rhythm.

Lesson 05

Principles

Hard-won rules — every one was paid for with a real mistake. Half of this only clicks after your first project; re-read it then.

  1. Short sessions, fresh starts

    One task, one session. Done = commit = new session. Long meandering sessions end in the dumb zone, and the dumb zone ends in mess.

  2. Log everything

    Keep a running log.md in every project: date, what was done, what's next. Every future session — yours and Claude's — starts from the log instead of from zero. The habit that compounds most.

  3. Mistakes are architecture problems, not AI problems

    When Claude keeps getting something wrong, the cause is usually upstream: messy folder, missing CLAUDE.md rule, ambiguous plan. Don't scold the model — fix the setup.

  4. Do not trust — verify

    Confident and correct are different things. Check claims, open outputs, run the thing. Trust grows per-task-type as verification keeps passing; it's never granted globally.

  5. Ask until you understand

    When Claude does something you don't follow, ask it to explain — a patient teacher with infinite time. Never accept magic.

  6. Caps on everything, day one

    Spending limits on every account and API before first use. A cap turns "catastrophe" into "hm, hit my limit." Adding a paid API later: look up the official price, multiply by your request count, check the number before running anything in bulk.

  7. Plan first; let Claude write the brief

    Messy idea → "write me a clear prompt for this" → correct the plan. The single biggest quality lever a beginner has.

  8. Context is the real skill

    You're not writing clever prompts; you're deciding what the model gets to see. A mediocre prompt with the right context beats a brilliant prompt with the wrong one.

  9. Teach the system, not just yourself

    Corrected Claude twice on the same thing? Put it in CLAUDE.md. Explained a workflow twice? Make it a skill. Captured lessons compound like interest.

  10. Close the loop

    The endgame: define "done" so clearly that Claude can check its own work and retry until it passes. Experts stop writing prompts and start designing loops. Plant the flag now; grow into it.

  11. Finish things

    No half-features. A small finished project teaches more than three abandoned ambitious ones.

The three you'll break first (everyone does): #1, #4, #11. Breaking them once and understanding why the rule exists — that's the lesson working.

Lesson 06

Your first project: a personal site, live on the internet

Session 4, done together. Not a toy: it runs the entire stack and the entire workflow, and ends with a URL you can send to anyone.

  1. Decide the content — no computer

    Your name, one sentence about who you are, 2–4 things you want to show. A site with real content teaches; "Lorem ipsum" doesn't.

  2. Create the repo

    On GitHub: New → name it mysite → Public → add a README → Create. Then in the terminal: git clone https://github.com/YOU/mysite.git

  3. Open the workshop

    Open the folder in VS Code, start claude in its terminal.

  4. Plan

    "I want a simple one-page personal site about me. I'm a complete beginner. Ask me questions until you understand, then propose a plan. Don't build anything yet." Read the plan; correct it — this is the cheap moment to change your mind.

  5. Standing instructions

    "Before you build: write a CLAUDE.md for this project — what the site is, that I'm a beginner, and that you should explain as you go." Your first CLAUDE.md; every project gets one.

  6. Build

    "Build the plan." Watch the loop happen. It ends by telling you how to see the site locally.

  7. Verify

    Look at it like a stranger: read every word aloud, make the window phone-narrow, click everything. Two or three rounds of concrete change requests is exactly how this is supposed to feel.

  8. Deploy

    "Commit everything with a clear message and push." Then on Vercel: Add New → Project → pick your repo → Deploy. One minute later: open the URL on your phone. It's really on the internet.

  9. The moment it clicks

    Change one word. Commit, push, watch your phone refresh. Edit → live in 60 seconds, and you never touched a server. This loop is what you now own.

After: one improvement per week, each a full plan→deploy loop. Small, finished, shipped.

Lesson 07

References

A deliberately short list. Five good sources beat fifty bookmarks.

People

Karpathy
Andrej Karpathy — the best explainer of what LLMs actually are. Watch "Intro to Large Language Models" (~1h) first; "Software 3.0" explains why this course exists.
Pocock
Matt Pocock (aihero.dev) — practical AI-assisted development; source of the "dumb zone".
Willison
Simon Willison (simonwillison.net) — the most grounded running commentary on what these tools can and can't do. No hype.
Anthropic
Anthropic engineering blog — "Claude Code: Best practices for agentic coding" once you're up and running; the Claude Code docs' Getting Started before session 2.

Keep learning after session 5

Ship weekly — one small finished improvement beats a course binge. Ask Claude itself ("explain MCP like I'm new" beats most blog posts — it can demo the answer). Steal patterns, not code. And re-take the ladder every few months.
